# PrepPal — Implementation Structure & Reference Guide

**Companion document to `PrepPal-System-Design-Specification.md`.**
This file is the ground-truth reference for directory layout, backend file structure, database schema (copy-paste-ready Prisma), and the complete API contract — written so that whoever (or whatever AI) implements this stays consistent phase-to-phase instead of re-deriving structure each time.

**Rule for implementation sessions:** before generating any new file, check this document for where it belongs and what it should be named. Don't invent parallel structures (e.g., a second `utils` folder, a different error-response shape) — extend what's here.

## 2. Backend Module Breakdown (File-by-File Responsibilities)

**Every module follows the same 4-file pattern** (5 for coding/resume which need extra pieces) — this consistency is intentional so an AI assistant (or a new contributor) can predict where logic goes without re-reading the whole codebase each time:

| File | Responsibility | Never Contains |
|---|---|---|
| `*.routes.ts` | Maps HTTP method+path → controller function, applies middleware (authGuard, roleGuard, rateLimiter, validateRequest) | Business logic |
| `*.controller.ts` | Parses `req`, calls the matching service method, wraps result in the response envelope | Direct DB queries, direct Prisma calls |
| `*.service.ts` | All business logic: validation beyond schema, orchestration across repositories/other services, calls to Prisma/queues/AI | HTTP-specific code (`req`/`res` objects) |
| `*.dto.ts` | Zod schemas for request bodies/params/query — the single source of truth for what's a valid request | Business logic |
| `*.repository.ts` (jobs, coding — where queries get complex enough to isolate) | Raw Prisma queries, kept separate from service logic so services stay testable without a real DB | Validation, business rules |

### 2.1 `modules/auth/`
- `auth.routes.ts`: `POST /register`, `POST /login`, `POST /refresh`, `POST /logout`
- `auth.service.ts`: hash/verify password (bcrypt), issue JWT pair, rotate refresh tokens (stores/checks blacklist in Redis)
- `jwt.strategy.ts`: sign/verify helpers used by `authGuard` middleware

### 2.2 `modules/users/`
- Profile CRUD (bio, education, skills, projects, experience) — one table, `Profiles`, updated via `PATCH /users/me`

### 2.3 `modules/jobs/`
- `jobs.repository.ts` isolates the search/filter/pagination query (it's the most complex query in the app — full-text search + multiple optional filters + cursor pagination)
- `jobs.service.ts` also computes `matchScore` per job for the logged-in user (calls the same matching function used in `resume` module's JD-comparison, kept in `packages/validation` or a shared `matching` util to avoid duplicating logic)

### 2.4 `modules/applications/`
- Enforces the unique `(jobId, userId)` constraint at the service layer with a friendly error before hitting the DB constraint
- Emits a notification-queue job on every status change

### 2.5 `modules/coding/`
- `problems/`: CRUD (admin-only for write), public read
- `submissions/`: `submissions.service.ts` writes the `PENDING` row and enqueues a job — **it never calls Judge0 directly**; only `workers/submission-worker.ts` does, keeping the API responsive under load
- `judge0-client/judge0.client.ts`: the only file in the entire codebase allowed to make HTTP calls to Judge0 — enforced by convention, not code, so keep this a strict habit
- `verdict-mapper.ts`: translates Judge0's numeric `status.id` into PrepPal's `Verdict` enum (single source of truth for this mapping — don't inline it elsewhere)

### 2.6 `modules/resume/`
- `text-extractor.ts`: pdf-parse/mammoth, isolated so it's easy to swap in `tesseract.js` for scanned PDFs later without touching the rest of the module
- `ats-scoring-engine.ts`: **pure function**, `(parsedResume, jobDescription?) => AtsScoreBreakdown` — deterministic, no AI, no I/O, fully unit-testable in isolation. This is the file most worth writing tests for first.
- `resume.service.ts` orchestrates: extract → call `ai.client` for parsing → run `ats-scoring-engine` → optionally call `ai.client` again for suggestions

### 2.7 `modules/ai/`
- `ai.client.ts` exposes one function used by every other module: `generateStructured<T>(prompt: string, schema: ZodSchema<T>, options?): Promise<T>`
- `fallback.ts` implements: try primary provider → catch 429/5xx → try secondary provider → catch again → throw a typed `AiUnavailableError` that calling services must handle gracefully (e.g., resume analysis shows "try again in a few minutes" rather than a raw 500)
- **Convention: no module outside `ai/` ever imports the Gemini or Groq SDK directly.** All AI calls go through `ai.client.ts`.

### 2.8 `modules/interviews/`
- `interviews.service.ts` holds the turn-based loop: create session → generate Q1 → on each answer, evaluate + generate next Q (adaptive difficulty logic lives here, not in the AI module — the AI module only executes prompts, it doesn't decide *what* prompt to send)

### 2.9 `modules/notifications/`
- Pure consumer-facing CRUD (`GET /notifications`, `PATCH /notifications/:id/read`) — the actual *creation* of notifications happens inside other services (`applications.service.ts`, `interviews.service.ts`) which enqueue a job that `notification-worker.ts` turns into a DB row + optional email

### 2.10 `modules/admin/`
- Thin — mostly calls into other modules' services with elevated permission checks already passed by `roleGuard`, rather than duplicating logic (e.g., job moderation calls `jobs.service.updateStatus()`, doesn't reimplement it)

## 3. Database Schema (Full Prisma Schema)

```prisma
// apps/api/prisma/schema.prisma

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

generator client {
  provider = "prisma-client-js"
}

// ─────────────────────────────────────────────
// ENUMS
// ─────────────────────────────────────────────

enum Role {
  STUDENT
  RECRUITER
  ADMIN
}

enum JobStatus {
  PENDING_MODERATION
  PUBLISHED
  REJECTED
  CLOSED
}

enum ApplicationStatus {
  APPLIED
  UNDER_REVIEW
  SHORTLISTED
  REJECTED
  HIRED
}

enum ProblemDifficulty {
  EASY
  MEDIUM
  HARD
}

enum ProblemStatus {
  DRAFT
  PUBLISHED
}

enum Verdict {
  PENDING
  ACCEPTED
  WRONG_ANSWER
  TIME_LIMIT_EXCEEDED
  RUNTIME_ERROR
  COMPILATION_ERROR
  MEMORY_LIMIT_EXCEEDED
}

enum Language {
  CPP
  JAVA
  PYTHON
  JAVASCRIPT
}

enum InterviewType {
  TECHNICAL
  DSA
  HR
  BEHAVIORAL
  ROLE_SPECIFIC
}

enum InterviewDifficulty {
  BEGINNER
  INTERMEDIATE
  ADVANCED
}

enum InterviewStatus {
  IN_PROGRESS
  COMPLETED
}

enum NotificationType {
  APPLICATION_STATUS
  INTERVIEW_RESULT
  JOB_MODERATION
  SYSTEM
}

// ─────────────────────────────────────────────
// CORE / AUTH
// ─────────────────────────────────────────────

model User {
  id            String   @id @default(uuid())
  email         String   @unique
  passwordHash  String
  role          Role
  name          String
  avatarUrl     String?
  isVerified    Boolean  @default(false)
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  profile              Profile?
  company              Company?
  resumes              Resume[]
  submissions          Submission[]
  applications         Application[]
  interviewSessions    InterviewSession[]
  notifications        Notification[]

  @@index([email])
}

model Profile {
  id        String   @id @default(uuid())
  userId    String   @unique
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  bio       String?
  education Json?    // [{ degree, institution, year, cgpa }]
  projects  Json?    // [{ title, description, techStack, link }]
  experience Json?   // [{ role, company, duration, description }]
  links     Json?    // { github, linkedin, portfolio }
  skillTags Skill[]  @relation("ProfileSkills")
  updatedAt DateTime @updatedAt

  @@index([userId])
}

model Skill {
  id       String    @id @default(uuid())
  name     String    @unique
  category String?
  profiles Profile[] @relation("ProfileSkills")
}

// ─────────────────────────────────────────────
// RECRUITER / JOBS
// ─────────────────────────────────────────────

model Company {
  id          String   @id @default(uuid())
  recruiterId String   @unique
  recruiter   User     @relation(fields: [recruiterId], references: [id], onDelete: Cascade)
  name        String
  logoUrl     String?
  website     String?
  industry    String?
  verified    Boolean  @default(false)
  jobs        Job[]

  @@index([recruiterId])
}

model Job {
  id           String        @id @default(uuid())
  companyId    String
  company      Company       @relation(fields: [companyId], references: [id], onDelete: Cascade)
  title        String
  description  String
  requirements String[]
  skills       String[]
  location     String?
  salaryMin    Int?
  salaryMax    Int?
```

**Notes on choices:**
- `education`, `projects`, `experience`, `links` on `Profile` are `Json` fields rather than separate tables — this is a deliberate MVP simplification (fewer joins, faster to build); if you later need to *query* across all users' education entries (e.g., "find everyone from X college"), promote them to real tables then, not before.
- `Skill` is a many-to-many lookup table so skill names stay canonical for matching (§4.4 of the main spec), while still allowing new skills to be added freely by users (service layer does `findOrCreate` on skill name).
- All `id` fields use `uuid()` rather than auto-increment ints — avoids leaking sequential IDs (e.g., total user count) via the API, and works cleanly across Neon/Supabase.

## 4. Complete API Reference

**Base URL convention:** `https://api.preppal.<domain>/v1/...` — version-prefixed from day one so breaking changes don't require a big-bang migration later.

**Response envelope (all endpoints):**
```jsonc
// success
{ "success": true, "data": { /* ... */ } }

// error
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "email is required" } }
```

### 4.1 Auth — `/v1/auth`

| Method | Path | Auth | Body | Response |
|---|---|---|---|---|
| POST | `/register` | None | `{ email, password, name, role: "STUDENT"\|"RECRUITER" }` | `{ user, accessToken }` (refresh set as httpOnly cookie) |
| POST | `/login` | None | `{ email, password }` | `{ user, accessToken }` |
| POST | `/refresh` | Refresh cookie | — | `{ accessToken }` |
| POST | `/logout` | Access token | — | `{ success: true }` (blacklists refresh token in Redis) |

### 4.2 Users — `/v1/users`

| Method | Path | Auth | Body | Response |
|---|---|---|---|---|
| GET | `/me` | Student/Recruiter | — | Full profile object |
| PATCH | `/me` | Student/Recruiter | `{ bio?, education?, projects?, experience?, links?, skills?[] }` | Updated profile |
| GET | `/me/dashboard` | Student | — | `{ codingStats, atsScore, interviewStats, roadmap[] }` (aggregated performance profile) |

### 4.3 Jobs — `/v1/jobs`

| Method | Path | Auth | Body/Query | Response |
|---|---|---|---|---|
| GET | `/` | Optional | `?query=&location=&skills=&minSalary=&sort=&page=&limit=` | `{ jobs[], total, page, limit }` |
| GET | `/:id` | Optional | — | Full job detail |
| POST | `/` | Recruiter | `{ title, description, requirements[], skills[], location?, salaryMin?, salaryMax? }` | Created job (status: PENDING_MODERATION) |
| PUT | `/:id` | Recruiter (owner) | Same as POST | Updated job |
| DELETE | `/:id` | Recruiter (owner) | — | `{ success: true }` |
| GET | `/recommended` | Student | — | Jobs sorted by matchScore for current user |
| GET | `/:id/applicants` | Recruiter (owner) | `?status=&sort=` | `{ applicants[] }` (joined with matchScore, atsScore) |

### 4.4 Applications — `/v1/applications`

| Method | Path | Auth | Body | Response |
|---|---|---|---|---|
| POST | `/jobs/:jobId/apply` | Student | `{ resumeId }` | Created application |

| GET | `/problems` | Optional | `?difficulty=&topics=&page=&limit=` | `{ problems[] }` (list view, no test cases) |

## 5. Shared Conventions

### 5.1 Naming
- **Files**: `kebab-case.type.ts` (e.g., `ats-scoring-engine.ts`, `jobs.service.ts`)
- **Prisma models**: PascalCase singular (`User`, not `Users`)
- **DB columns**: camelCase (Prisma default maps cleanly to Postgres)
- **REST routes**: plural nouns, kebab-case for multi-word (`/interview-questions` if ever needed, though current design avoids this)
- **Enums**: SCREAMING_SNAKE_CASE values, PascalCase enum name

### 5.2 Error Codes (extend this list as needed, don't invent one-off strings)
`VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT` (e.g., duplicate application), `RATE_LIMITED`, `AI_UNAVAILABLE`, `INTERNAL_ERROR`

### 5.3 HTTP Status Mapping
| Situation | Status |
|---|---|
| Success (sync) | 200 |
| Created | 201 |
| Accepted (async, e.g., submission queued) | 202 |
| Validation failure | 400 |
| Missing/invalid auth | 401 |
| Authenticated but wrong role/owner | 403 |
| Resource not found | 404 |
| Duplicate/conflict (e.g., already applied) | 409 |
| Rate limit hit | 429 |
| Unhandled server error | 500 |

### 5.4 Pagination Convention (used identically everywhere)
Query params: `?page=1&limit=20` (limit capped at 50 server-side regardless of what's requested). Response always includes `{ data: [...], total, page, limit }` inside the envelope's `data`.

### 5.5 Git/Commit Convention
Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`), one module per PR where possible during Phases 4–8 so review stays scoped to the roadmap phase being built.
