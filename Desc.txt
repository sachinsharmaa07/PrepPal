## 1. Product Overview

### 1.1 What PrepPal Is

PrepPal is a unified **placement preparation + hiring platform** that merges three things students and recruiters currently juggle across separate tools: a **competitive coding practice platform** (like LeetCode/HackerRank), an **AI-powered resume/ATS analyzer** (like Rezi/Teal), and an **AI mock interview system** (like Pramp/Interviewing.io) — all connected to a **real job portal** where the data generated by practice actually feeds into applications.

The core insight: today these tools are disconnected. A student practices DSA on one site, builds a resume on another, mock-interviews on a third, and applies to jobs on a fourth — with no single system that knows their skill level, resume gaps, and interview weaknesses at once. PrepPal closes that loop: what you solve, how your resume scores, and how your mock interviews go all feed a single **performance profile** that recruiters can see (with consent) and that drives personalized recommendations back to the student.

### 1.2 The Problem It Solves

- Students don't know if they're "job ready" — no single objective signal.
- Resumes get silently rejected by ATS systems with no explanation.
- Interview practice is either non-existent or unstructured (no feedback loop).
- Recruiters can't efficiently evaluate candidates beyond a static resume/PDF.
- Placement cells / campus programs lack a data-driven way to track cohort readiness.

### 1.3 Target Users

| User | Need |
|---|---|
| Students / job seekers (primary) | Practice, resume feedback, mock interviews, apply to jobs, track readiness |
| Recruiters / companies | Post jobs, see ranked/matched candidates, review resumes and coding performance |
| Admins (platform/campus) | Moderate jobs, manage problems, view analytics, ensure platform integrity |

### 1.4 Main User Journeys

1. **Student journey:** Register → build profile → practice DSA problems → upload resume → get ATS score + suggestions → take AI mock interview → view weaknesses → search & apply to jobs → track applications → get notified of status changes.
2. **Recruiter journey:** Register company → post job with requirements → review applicants ranked by match score → view resume + coding/interview signals → change application status → hire.
3. **Admin journey:** Moderate job postings → manage problem bank → monitor reports/abuse → view platform-wide analytics.

### 1.5 How Features Connect

```
Coding Practice ─┐
                  ├─→ Performance Profile ─→ Job Matching ─→ Recruiter View
Resume/ATS ───────┤
                  │
AI Interviews ────┘
```

The **Performance Profile** is the connective tissue: submissions (verdicts, difficulty, topics), resume/ATS scores, and interview scores all write into one aggregate record used for (a) student-facing dashboards/roadmaps and (b) recruiter-facing candidate ranking.

### 1.6 Differentiation from a Normal Placement-Prep Site

- Single account, single data model — not three disconnected tools glued together.
- AI is used for **specific, bounded tasks** (resume parsing, ATS scoring, interview Q&A, evaluation) rather than as an unstructured chatbot bolt-on.
- Real job-portal lifecycle (not just "practice"), so the platform has genuine two-sided value (students + recruiters).
- Designed with a real system-design architecture (auth, caching, queues, observability) — demonstrating production engineering, not just CRUD.

## 3. Coding Platform

### 3.1 Reusing `codesach`

Since `codesach` already implements problem management, submission handling, and likely a Judge0 integration, the reuse strategy is:

1. **Treat `codesach`'s backend logic as the seed for a `coding-service` module** inside PrepPal's backend (or a separate service if you go modular-monolith route — see §7).
2. Audit `codesach` for: problem schema, test-case schema, submission schema, Judge0 client code, verdict-mapping logic. These are almost directly portable — the domain doesn't change.
3. Re-point its database layer to PrepPal's shared database (same Postgres instance, dedicated schema/tables) instead of a standalone DB, so submissions can join with PrepPal's `users` table for the performance profile.
4. Wrap its submission endpoints behind PrepPal's own auth middleware (JWT) instead of whatever auth `codesach` had, so identity is unified.
5. Keep its frontend code editor component (likely Monaco-based) and port it into PrepPal's React frontend as a shared `CodeEditor` component.

### 3.2 Problem Management

- **Problem**: title, statement (markdown), difficulty (easy/medium/hard), topics/tags, constraints, sample I/O, time limit, memory limit, author (admin), status (draft/published).
- **Test cases**: input/output pairs, marked `sample` (visible) or `hidden` (used for judging only), stored in object storage (S3) if large, else in DB.

### 3.3 Code Editor

- Monaco Editor (VS Code's editor) embedded in React, language selection dropdown, theme, auto-indent, run-sample-tests button (client-triggered, calls backend), submit button.

### 3.4 Supported Languages (via Judge0)

MVP: **C++, Java, Python, JavaScript**. Judge0 supports 60+ languages out of the box — expand later by just adding language IDs to a config map, no new infra needed.

### 3.5 Submission System & Flow

```
User writes code (Monaco editor)
   ↓
Frontend → POST /submissions {problemId, language, code}
   ↓
Backend (Submission Service)
   - validates request, checks rate limit (e.g., 1 submission / 3s per user)
   - fetches problem + test cases
   - creates Submission row (status = PENDING)
   - pushes job to queue (BullMQ/SQS) → returns submissionId immediately (202 Accepted)
   ↓
Background Worker (Submission Consumer)
   - pulls job from queue
   - for each test case: calls Judge0 (Docker container) with code + input
   - Judge0 compiles + executes in an isolated sandbox, enforces time/memory limits
   - collects Judge0 verdicts per test case (Accepted, Wrong Answer, TLE, RE, CE, MLE)
   ↓
Worker aggregates verdicts → final verdict (first failing test wins, or All Passed)
   ↓
Updates Submission row in DB (status = COMPLETED, verdict, runtime, memory)
   ↓
Notifies frontend (WebSocket/polling) → Frontend shows result
   ↓
Performance Profile updated (async) — topic mastery, streaks, etc.
```

### 3.6 Compilation & Runtime Handling

- **Compilation errors**: Judge0 returns status `Compilation Error` with stderr — shown directly to user, no test cases run.
- **Runtime errors**: Judge0 returns `Runtime Error (NZEC)` etc. with stderr for the failing test case only (hidden test stderr can be redacted to avoid leaking hidden inputs).
- **Time limits**: set per-problem (default 1–2s), enforced by Judge0's `cpu_time_limit`.
- **Memory limits**: set per-problem (default 256MB), enforced by Judge0's `memory_limit`.

### 3.7 Verdict System

`Accepted (AC)`, `Wrong Answer (WA)`, `Time Limit Exceeded (TLE)`, `Runtime Error (RE)`, `Compilation Error (CE)`, `Memory Limit Exceeded (MLE)`.

### 3.8 Submission History

Per-user, per-problem submission log: language, verdict, runtime, memory, timestamp, code (stored for review). Indexed by `(userId, problemId, createdAt)`.

### 3.9 Leaderboard

Appropriate **only for contests**, not for general practice (avoids turning practice into a vanity metric). MVP: skip. Advanced: per-contest leaderboard ranked by (problems solved desc, penalty time asc) — classic ICPC-style scoring.

### 3.10 Securely Executing Untrusted Code

This is the highest-risk component of the platform. Layers of defense:

1. **Judge0 itself runs each submission in an isolated container** (uses `isolate`, a sandbox built on Linux namespaces + cgroups) — this is Judge0's core design, not something you build yourself.
2. **Run Judge0 in its own Docker network**, with **no internet access** from the execution containers (block outbound network in the sandbox — Judge0 supports disabling network per submission).
3. **Resource limits**: CPU time, wall time, memory, stack size, max file size, max number of processes — all configured per submission via Judge0's API parameters. Prevents fork bombs and infinite loops from taking down the host.
4. **Run Judge0 workers as non-root**, on a **dedicated EC2 instance or ECS task separate from the main API** — so a sandbox escape doesn't have direct access to the database or app servers. This is why Judge0 sits in its own subnet/security group in the AWS design (§10).
5. **Never expose Judge0's HTTP API directly to the internet** — only PrepPal's backend (submission service) can reach it, over a private network/VPC.
6. **Input size limits** on submitted code and stdin to prevent resource exhaustion.
7. **Queue-based rate limiting** — cap concurrent submissions per user and total system-wide concurrency, so one user can't flood the worker pool.

## 4. AI Resume/CV System

### 4.1 Pipeline

```
CV Upload (PDF/DOCX)
   ↓
Object Storage (S3) — original file stored, versioned
   ↓
Text Extraction (pdf-parse / mammoth for docx, or AWS Textract for scanned PDFs)
   ↓
Parsing (structure raw text into sections: contact, education, experience, skills, projects)
   ↓
AI Analysis (LLM call: structured extraction + qualitative review)
   ↓
ATS Scoring (rule-based engine, deterministic, NOT purely AI)
   ↓
Job Matching (compare parsed CV against a specific JD, if selected)
   ↓
Suggestions (LLM generates specific, actionable improvement points)
   ↓
Optimized CV (user-approved edits → regenerate resume, optionally re-render to PDF)
```

### 4.2 What Data Is Extracted

Contact info, education entries, work experience entries, project entries, skills (technical + soft), certifications, total years of experience (derived), summary/objective text.

### 4.3 ATS Scoring Methodology

**Important design decision: ATS scoring should be primarily rule-based/deterministic, with AI used only to assist extraction and phrasing feedback.** Real ATS systems (Workday, Greenhouse, Taleo) score on parseable structure and keyword match, not "AI judgment" — so mimicking that requires deterministic rules, otherwise the score isn't meaningfully "ATS-like" and becomes unfalsifiable.

Score components (example weighting):

| Component | Weight | Logic |
|---|---|---|
| Keyword match | 35% | Overlap between resume tokens and JD tokens (or general role-keyword bank if no JD selected) |
| Skill match | 25% | Overlap between declared/extracted skills and required skills |
| Formatting/parseability | 20% | Penalize tables, images, multi-column layouts, non-standard fonts, missing section headers (checked via structure of extracted text vs. expected sections) |
| Section completeness | 10% | Has contact/education/experience/skills sections present |
| Quantified achievements | 10% | Regex/NLP check for numbers/metrics in bullet points ("increased X by 30%") |

### 4.4 Keyword & Skill Matching

- Tokenize both CV text and JD text, normalize (lowercase, stem/lemmatize), remove stopwords.
- Compute overlap using a weighted set intersection (exact match) for MVP; **cosine similarity over embeddings** for a more advanced/fuzzy match (e.g., "React.js" ≈ "ReactJS" ≈ "React") in the advanced phase.

### 4.5 Missing Keywords & Formatting Checks

- Diff JD keyword set minus CV keyword set → "missing keywords" list shown to user.
- Formatting checks are static rules against the extracted text/layout (e.g., "no email found", "experience section not detected", "resume uses a table layout that may not parse in ATS systems").

### 4.6 AI Suggestions & Optimization

LLM prompt takes: parsed CV JSON + ATS score breakdown + (optional) JD text → returns structured suggestions: "add missing keyword X to your skills section", "quantify this bullet: '...'", "your summary is too generic, consider: ...". These are **suggestions only** — the user must approve edits before they're applied to any stored resume.

### 4.7 Which AI Models/APIs (Free-Tier Only)

Since budget is zero, every AI call must run on a **free-tier LLM provider**. The two realistic options:

- **Google Gemini API (free tier)** — `gemini-2.0-flash` / `gemini-1.5-flash` class models. Free tier gives a workable number of requests/day (check current limits at ai.google.dev, they change over time) and supports structured/JSON output mode natively, which is exactly what's needed for resume parsing and interview evaluation.
- **Groq API (free tier)** — extremely fast inference on open models (Llama 3.x, Mixtral, Gemma) hosted on Groq's LPU hardware. Great for anything latency-sensitive (interview Q&A feels conversational) and has a generous free request allowance.

**Recommended split:**
| Task | Primary | Why |
|---|---|---|
| Resume parsing (unstructured → JSON) | Gemini free tier | Native structured-output/JSON mode, good instruction-following |
| ATS suggestion generation | Gemini free tier | Longer-context reasoning over resume + JD |
| Interview question generation | Groq free tier (Llama 3.x) | Fast responses keep the interview feeling conversational |
| Interview answer evaluation | Gemini free tier | Needs more careful structured rubric scoring |

**Multi-provider fallback is a first-class design requirement, not an optimization** — free tiers have low daily/per-minute rate limits, so the `ai` module should implement a provider-agnostic interface (`generateStructured(prompt, schema)`) with **automatic fallback**: try Gemini → on 429/rate-limit, retry via Groq → on failure, queue the request and retry later rather than failing the user's action outright. This also means never hard-coding a single provider's SDK into business logic — always go through this abstraction.

- Embeddings (advanced phase, fuzzy skill/JD matching): use a **free, self-hosted, open-source model** — `sentence-transformers` (e.g., `all-MiniLM-L6-v2`) run locally/in a small worker process. Avoid paid embedding APIs (OpenAI, Cohere) entirely; MiniLM is small enough to run on a free-tier CPU instance or even inside the existing worker container. For MVP, skip embeddings altogether and rely on exact/normalized keyword-set overlap (§4.4) — it's free and good enough to demonstrate the concept.
- Document parsing: `pdf-parse`/`pdfplumber` for text PDFs (free, local, no API cost). Avoid AWS Textract for scanned PDFs since it's pay-per-page — if scanned-resume support is needed, use a free OCR library (`tesseract.js`) instead, or simply reject scanned PDFs at MVP with a message asking for a text-based PDF.

### 4.8 Where AI Should and Should Not Be Trusted

| Trust AI for | Don't trust AI for (use rules/deterministic logic) |
|---|---|
| Extracting structure from messy free text | The final numeric ATS score (must be reproducible/explainable) |
| Writing suggestion text / rephrasing bullets | Pass/fail hiring decisions |
| Summarizing an interview performance | Anything security-sensitive (never let AI output control system behavior directly — always validate/sanitize) |
| Generating interview questions | Storing/trusting AI-extracted PII without validation |

Always validate LLM JSON output against a schema (e.g., Zod/Pydantic) before using it — never trust it blindly, and never execute or directly render raw LLM output without sanitization (prevents prompt-injection-via-resume-content from causing XSS or unwanted behavior).

## 5. Virtual AI Interview

### 5.1 Interview Types (MVP: Technical text-based; Advanced: rest)

- Technical (general programming concepts)
- DSA (algorithm problem walkthrough, verbal/textual reasoning, not necessarily full code)
- HR / Behavioral (STAR-method style questions)
- Role-specific (backend, frontend, data, etc. — templated question banks)
- Difficulty levels: Beginner / Intermediate / Advanced, selectable per session.

### 5.2 Architecture & Flow

```
User selects interview type + difficulty
   ↓
Frontend → POST /interviews {type, difficulty, role}
   ↓
Interview Service creates Interview session (DB row), calls LLM to generate
first question (seeded by type/difficulty/role + a question-bank fallback
to avoid pure hallucination for DSA problems)
   ↓
Frontend displays question → user answers (text, optionally voice→text via
Web Speech API/Whisper in advanced phase)
   ↓
Frontend → POST /interviews/:id/answer {questionId, answer}
   ↓
Interview Service:
   - stores answer
   - calls LLM: evaluate(question, answer, rubric) → {score, strengths,
     weaknesses, feedback}
   - stores evaluation
   - calls LLM: generate next question (informed by previous answer quality —
     easier if struggling, harder if excelling — adaptive difficulty)
   ↓
Repeats for N questions (configurable, e.g., 5–8)
   ↓
On completion: Interview Service aggregates per-question scores →
overall score + weakness summary + recommendations
   ↓
Result stored → Performance Profile updated → shown on dashboard
```

### 5.3 Answer Evaluation & Scoring

Each answer evaluated against a **rubric** (correctness, clarity, completeness, depth) via structured LLM prompt returning JSON: `{score: 0-10, strengths: [...], weaknesses: [...], missed_points: [...]}`. Scores aggregated (average or weighted by difficulty) into a session score.

### 5.4 Weakness Detection & Recommendations

Aggregate `weaknesses`/`missed_points` across all answers in a session (and across sessions over time) → cluster by topic (e.g., "recursion", "system design basics") → feed into the **Placement Roadmap** feature (§2.1) as concrete next steps, and optionally suggest specific coding problems by topic.

### 5.5 Interview History

Store every session: type, difficulty, questions asked, answers, per-question scores, overall score, timestamp — viewable in a history timeline on the dashboard.

## 6. Job Portal

### 6.1 Job Lifecycle

```
Recruiter creates job (status: PENDING_MODERATION)
   ↓
Admin reviews → Approve (status: PUBLISHED) or Reject (status: REJECTED, reason)
   ↓
Candidate searches/filters jobs (only PUBLISHED shown)
   ↓
Candidate applies → Application created (status: APPLIED), resume snapshot linked
   ↓
Recruiter dashboard shows applicants, sorted by match score
   ↓
Recruiter changes status (UNDER_REVIEW → SHORTLISTED → REJECTED/HIRED)
   ↓
Notification sent to candidate on every status change
```

### 6.2 Search, Filtering, Pagination, Sorting

- **Search**: full-text search on title/description (Postgres `tsvector`/GIN index for MVP; consider Elasticsearch/OpenSearch only if search complexity grows — avoid over-engineering).
- **Filtering**: by location, skill tags, experience level, salary range, company.
- **Pagination**: cursor-based or offset+limit with `LIMIT/OFFSET` and a max page size (e.g., 20), always indexed on the sort column.
- **Sorting**: newest first (default), or by match score (when logged in and profile complete).

### 6.3 Job Recommendations & Candidate-Job Matching

Match score = weighted overlap of candidate skills/profile vs job requirements (same matching engine as CV-JD matching in §4.4, reused). Recommendations = top-N unapplied published jobs by match score for the logged-in candidate.

### 6.4 Recruiter Dashboard

Per-job applicant list with columns: candidate name, match score, ATS score (if resume analyzed), applied date, status — sortable/filterable, with quick actions to change status.

## 7. System Design (High-Level Architecture)

### 7.1 Architecture Choice: **Modular Monolith**

For a 4th-year portfolio project, **full microservices are inappropriate** — they add operational overhead (multiple deployments, service discovery, distributed tracing, network failure modes) without a real scaling need at this stage, and they will actively hurt you in interviews if you can't justify *why* you split services.

**Recommendation: a modular monolith**, structured as clearly separated internal modules (auth, users, jobs, applications, coding, resume, ai, interviews, notifications) inside **one backend codebase**, sharing one database (with clear schema boundaries per module) — but with **two things pulled out as genuinely separate services** because they have fundamentally different operational characteristics:

1. **Judge0 (code execution)** — must be isolated for security (§3.10), and has completely different resource/scaling needs (CPU-bound, sandboxed) than the API server.
2. **Background worker(s)** for async jobs (submission grading, AI calls, email notifications) — separated so slow AI/LLM calls or Judge0 polling never block the request/response cycle of the main API.

This gives you a **"modular monolith + 2 auxiliary services"** — realistic, defensible, and still lets you talk fluently about microservices trade-offs without having built ten services you can't actually explain deeply.

### 7.2 Major Components

| Component | Role |
|---|---|
| Frontend (React/Next.js) | UI, client-side routing, calls Backend API |
| Backend API (modular monolith) | REST API: auth, users, jobs, applications, resume, interview orchestration |
| Coding/Submission Service | Receives submissions, queues them, talks to Judge0 |
| Judge0 (isolated) | Compiles/executes untrusted code in sandboxes |
| AI Service (module, not separate deployable in MVP) | Wraps LLM calls (resume analysis, interview Q&A/eval) via Gemini/Groq free tiers, with prompt templates + schema validation + provider fallback |
| Notification Service (module) | Sends email (free tier: Resend or Brevo, ~100–300 free emails/day — instead of paid AWS SES) + creates in-app notification rows; consumes queue events |
| Database (PostgreSQL — Neon/Supabase free tier) | Primary relational store for all modules |
| Cache (Redis — Upstash free tier) | Session/rate-limit counters, hot job listings, leaderboard (if built) |
| Object Storage (S3 — AWS free tier, 5GB/12mo) | Resumes, profile images, problem test-case files |
| Message Queue (BullMQ on Upstash Redis) | Async submission grading, AI calls, email sending |
| Background Workers | Consume queue jobs (submission grading, AI analysis, notifications) |
| Monitoring/Logging | CloudWatch (AWS) + structured JSON logs; optional Sentry for error tracking |

### 7.3 Component Communication

- Frontend ↔ Backend API: REST over HTTPS, JWT in `Authorization` header.
- Backend ↔ Judge0: internal HTTP call over private network (VPC-internal, no public exposure).
- Backend ↔ Queue ↔ Workers: async, decoupled — API just enqueues and returns a job/submission ID; workers process and update DB, frontend polls or uses WebSocket/SSE for live updates.
- Backend ↔ Database: via ORM (Prisma/Drizzle for Node, or SQLAlchemy if Python), connection pooling (PgBouncer if scaling later).
- Backend ↔ S3: pre-signed URLs for upload/download (never proxy large files through the API server).
- Backend ↔ AI provider: outbound HTTPS to Anthropic/OpenAI API, with timeouts + retries.

### 7.4 System-Design Concepts Applied

| Concept | Where used |
|---|---|
| Modular monolith vs microservices | Overall architecture choice (§7.1), explained trade-off |
| REST APIs | All client-facing endpoints |
| AuthN/AuthZ | JWT-based auth + RBAC (student/recruiter/admin) |
| JWT/session mgmt | Access token (short-lived, 15 min) + refresh token (httpOnly cookie, 7 days) |
| Caching | Redis for job listing hot-path, rate-limit counters, session blacklist |
| DB indexing | Composite indexes on (userId, createdAt), GIN index for search |
| Pagination | Limit/offset with indexed sort columns on jobs, submissions |
| Rate limiting | Redis token-bucket per user/IP on submission + auth endpoints |
| Async processing | Submission grading, AI calls, email — all queued, not synchronous |
| Message queues | BullMQ (Redis-backed) for MVP; swappable for SQS in AWS-heavy deployment |
| Background workers | Dedicated worker process(es) consuming the queue |
| Horizontal scaling | Stateless API servers behind a load balancer; workers scale independently |
| Load balancing | AWS ALB / Render's built-in LB |
| Fault tolerance & retries | Queue jobs retry with exponential backoff (e.g., 3 attempts) on Judge0/LLM failures |
| Idempotency | Submission/application endpoints use idempotency keys to prevent duplicate processing on retry |
| API security | Input validation (Zod), helmet headers, CORS allowlist, rate limiting |
| File storage | S3 with pre-signed URLs, private buckets |
| Observability | Structured logs + CloudWatch metrics + basic dashboards |
| CI/CD | GitHub Actions: lint/test/build → deploy to Render/Vercel/AWS on merge to main |

| Technology | Why | Used By | Alternative |
|---|---|---|---|

### Database (Free Tier)

## 10. AWS Architecture

```
Internet
   │
   ▼
Route 53 (DNS) ──► ACM (TLS cert)
   │
   ▼
Public Subnet(s)
   ├── Application Load Balancer (public-facing, HTTPS)
   └── NAT Gateway (outbound internet for private subnet resources)
   │
   ▼
Private Subnet(s)  ── Application Layer
   ├── ECS Service: Judge0 workers (isolated, no public IP, no inbound
   │      from internet — only reachable from backend via internal ALB
   │      or service discovery)
   └── (Optional) ECS Service: Backend API / Workers, if not on Render
   │
   ▼
Private Subnet(s) ── Data Layer
   └── (No AWS-hosted DB/cache — PostgreSQL lives on Neon/Supabase and
        Redis on Upstash, both external free-tier serverless providers,
        reached over the internet from the backend, NOT inside this VPC)
   │
S3 (separate, not inside VPC — accessed via IAM + VPC Endpoint for
    private, no-NAT-cost access)
```

**Free-tier-first footprint:** to stay at $0 for the life of this project (beyond the standard AWS 12-month window), the AWS side is kept deliberately minimal — **just enough to host Judge0 securely and store files** — rather than a full RDS/ElastiCache buildout, since those don't have a genuinely free-forever tier. Database and cache live on dedicated free-tier serverless providers instead (§8), which is *also* more realistic for a student project: you get managed backups/scaling on the DB without paying for or babysitting an RDS instance.

### Components & Purpose

| Component | Purpose | Public? | Cost |
|---|---|---|---|
| VPC | Isolated network boundary for all AWS resources | — | Free (always) |
| Public subnet | Hosts ALB (if used), NAT Gateway | Yes | NAT Gateway has an hourly + data charge — **skip NAT Gateway for MVP** (see note below) |
| Private subnet(s) | Hosts Judge0 (single EC2 instance) | No | Free tier |
| Internet Gateway | Allows public subnet to reach/be reached by internet | — | Free (always) |
| Route tables | Direct traffic between subnets/IGW | — | Free |
| Security Groups | Firewall rules: Judge0 SG allows inbound only from the backend's known IP(s) + a shared-secret header check | — | Free (always) |
| EC2 (`t2.micro`/`t3.micro`, free tier) | Runs Judge0 via Docker Compose directly (simpler and cheaper than ECS/Fargate, which bills per vCPU-hour beyond a small free allowance) | No public IP needed if reached via bastion/VPN, or a locked-down public IP + SG allow-list for MVP simplicity | Free (750 hrs/month, 12 months) |
| S3 | Resume/file storage | No (private bucket, pre-signed URLs only) | Free (5GB, 12 months) |
| CloudWatch | Logs + metrics + alarms for the EC2 instance | — | Free tier covers basic logs/metrics for a single instance |
| IAM | Least-privilege roles/users (S3 access, no root usage) | — | Always free |
| SSM Parameter Store | Store DB/Redis connection strings, JWT secret, LLM API keys — never in code/env files in repo | — | Standard tier is always free (use this instead of Secrets Manager, which charges per secret/month) |
| Route 53 | DNS for custom domain (optional — a free subdomain from Vercel/Render works fine for a portfolio project) | Yes (DNS only) | ~$0.50/month per hosted zone if you want a custom domain — the one small optional cost in this whole stack |

**On skipping NAT Gateway:** NAT Gateway is one of the few AWS components with **no free tier at all** (hourly charge from hour one). Since the only private-subnet resource is the single Judge0 EC2 instance, and it doesn't need arbitrary outbound internet access for the sandbox itself (network is disabled inside the execution container regardless — §3.10), you can avoid NAT entirely by either (a) giving the EC2 instance itself a public IP but locking inbound traffic down hard via Security Group (only the backend's IP + a shared secret), or (b) using a VPC endpoint for S3 access instead of routing through NAT. This keeps the AWS bill at genuinely $0.

**Why AWS at all, then:** the only component that *needs* real network isolation for security reasons is Judge0 (§3.10) — that's the one piece worth keeping on AWS to demonstrate real VPC/security-group skills. Everything else is on free serverless providers because there's no security requirement forcing them onto AWS, and doing so would only add cost without adding to what you can demonstrate.

## 11. Vercel + Render + AWS — Combined Deployment

| Platform | What Runs There | Why |
|---|---|---|
| **Vercel** | Next.js frontend | Zero-config, free tier, automatic HTTPS, instant preview deployments per PR |
| **Render** | Backend API (Express/NestJS) + background workers (free tier) | Free tier, no VPC to manage for a service that doesn't need Judge0-level isolation |
| **Neon/Supabase + Upstash** | PostgreSQL + Redis | Genuinely free, no time-boxed expiry, no server management |
| **AWS (Free Tier)** | Judge0 (single EC2 instance in private/locked-down subnet) + S3 (resumes) + CloudWatch + SSM Parameter Store + IAM | Genuinely needs network isolation (Judge0) and durable object storage (S3); demonstrates cloud/VPC skills at $0 cost within the 12-month window |

### Communication

- **Frontend (Vercel) → Backend (Render):** REST calls over HTTPS to `api.preppal.yourdomain.com`, CORS configured on backend to allow only the Vercel domain (+ localhost in dev).
- **Backend (Render) → Judge0 (AWS):** Backend calls Judge0's HTTP API over the internet **but restricted** via AWS Security Group to only accept traffic from Render's known egress IPs (Render provides static outbound IPs on paid tiers) — or, more robustly, put Judge0 behind an internal ALB and use an AWS API Gateway with an API key that only the backend knows. For MVP simplicity: Judge0 exposed via a **private ALB reachable only via a VPN/allow-listed IP** is complex for Render's dynamic IPs — practical MVP compromise: **run Judge0 in a public subnet but firewalled by Security Group to only allow the Render service's IP range, plus require a shared-secret header** on every request as defense-in-depth.
- **Backend (Render) → S3 (AWS):** via AWS SDK using an IAM user with least-privilege (`s3:PutObject`, `s3:GetObject` on the specific bucket only), access keys stored in Render's built-in encrypted environment variables (free, no need to pay for Secrets Manager since the backend itself isn't inside the VPC — SSM Parameter Store is reserved for secrets consumed by the EC2/Judge0 side).
- **Backend (Render) → Neon/Supabase (Postgres) & Upstash (Redis):** standard connection string / REST API over TLS, provided free by each service — no networking cost, since neither lives inside the AWS VPC.
- **Backend (Render) → Gemini/Groq (AI):** outbound HTTPS calls with API keys in Render env vars; the `ai` module's fallback logic (§4.7) handles free-tier rate-limit responses (HTTP 429) by switching providers or queuing the request for retry.

### Domain Configuration

- Root domain (`preppal.com`) → Vercel (frontend) via A/ALIAS record.
- `api.preppal.com` → Render backend via CNAME.
- `judge.internal.preppal.com` (or just an AWS-provided endpoint, not a public brand domain) → Judge0, not exposed to end users at all, only referenced in backend config.

### CORS, Env Vars, Secrets, HTTPS

- CORS: backend allow-list = `[https://preppal.com, https://www.preppal.com]` (+ localhost in dev) — never `*` in production.
- Env vars: `.env` files **never committed**; Vercel/Render both have built-in encrypted env var storage; AWS secrets pulled via Secrets Manager at container start (not baked into the Docker image).
- HTTPS: Vercel and Render provide automatic TLS certs; AWS side uses ACM certs on the ALB if Judge0/API Gateway is exposed at all.
- Security implication of this 3-cloud split: **the weakest link is the Backend↔Judge0 hop**, since it crosses the public internet between two providers. Mitigate with shared-secret header + IP allow-listing + (ideally, advanced phase) migrating the backend itself into the same AWS VPC as Judge0 so that hop becomes fully private.

## 12. Database Design

### 12.1 Core Entities

**Users**
- Fields: `id, email (unique), passwordHash, role (student|recruiter|admin), name, avatarUrl, isVerified, createdAt`
- Relationships: 1—1 `Profile`, 1—1 `Company` (if recruiter), 1—N `Submissions`, 1—N `Applications`, 1—N `Resumes`, 1—N `InterviewSessions`
- Indexes: unique index on `email`
- Why: separate `Users` (auth-only) from `Profile` (rich data) keeps the auth table small/fast and lets profile schema evolve independently.

**Profiles**
- Fields: `id, userId (FK), bio, education[], skills[], links{github,linkedin}`
- Indexes: `userId` (unique FK)

**Companies**
- Fields: `id, recruiterId (FK), name, logoUrl, website, industry, verified`
- Indexes: `recruiterId`

**Jobs**
- Fields: `id, companyId (FK), title, description, requirements[], skills[], location, salaryMin, salaryMax, status (pending|published|rejected|closed), createdAt`
- Indexes: GIN index on `title+description` (full-text search), index on `(status, createdAt)` for listing queries, index on `skills` (GIN, array)

**Applications**
- Fields: `id, jobId (FK), userId (FK), resumeId (FK), status (applied|under_review|shortlisted|rejected|hired), matchScore, appliedAt`
- Indexes: unique composite `(jobId, userId)` (prevents duplicate applications), index on `(userId, appliedAt)`, index on `(jobId, status)`

**Resumes**
- Fields: `id, userId (FK), fileUrl (S3 key), version, uploadedAt, isActive`
- Indexes: `(userId, isActive)`

**ResumeAnalyses**
- Fields: `id, resumeId (FK), jobId (nullable FK), atsScore, keywordMatchScore, skillMatchScore, missingKeywords[], suggestions[], analyzedAt`
- Indexes: `resumeId`, `(resumeId, jobId)`
- Why nullable `jobId`: a resume can be analyzed generically (no JD) or against a specific job.

**Skills** (lookup/reference table)
- Fields: `id, name (unique), category`
- Why: normalizes free-text skills into a canonical set for reliable matching; user-declared skills reference this table where possible, with a fallback free-text tag for anything not yet catalogued.

**CodingProblems**
- Fields: `id, title, statementMd, difficulty, topics[], timeLimitMs, memoryLimitMb, status(draft|published), createdBy (FK admin)`
- Indexes: index on `(difficulty, topics)` for filtering

**TestCases**
- Fields: `id, problemId (FK), inputRef (S3 key or inline text), expectedOutputRef, isSample`
- Indexes: `problemId`

**Submissions**
- Fields: `id, userId (FK), problemId (FK), language, code, verdict, runtimeMs, memoryKb, createdAt`
- Indexes: composite `(userId, problemId, createdAt)`, `(problemId, verdict)` for problem-level stats

**Interviews (InterviewSessions)**
- Fields: `id, userId (FK), type, difficulty, role, status(in_progress|completed), overallScore, createdAt, completedAt`
- Indexes: `(userId, createdAt)`

**InterviewQuestions**
- Fields: `id, interviewId (FK), questionText, orderIndex, difficulty`
- Indexes: `interviewId`

**InterviewAnswers**
- Fields: `id, questionId (FK), answerText, score, strengths[], weaknesses[], answeredAt`
- Indexes: `questionId`

**Notifications**
- Fields: `id, userId (FK), type, message, isRead, createdAt`
- Indexes: `(userId, isRead, createdAt)`

### 12.2 ER-Style Conceptual Representation

```
Users (1)───(1) Profiles
  │
  ├──(1)───(1) Companies            [if role = recruiter]
  │
  ├──(1)───(N) Resumes ──(1)───(N) ResumeAnalyses ──(N)───(1) Jobs [nullable]
  │
  ├──(1)───(N) Submissions ──(N)───(1) CodingProblems ──(1)───(N) TestCases
  │
  ├──(1)───(N) Applications ──(N)───(1) Jobs
  │                              │
  │                              └──(N)───(1) Companies
  │
  ├──(1)───(N) InterviewSessions ──(1)───(N) InterviewQuestions
  │                                              │
  │                                              └──(1)───(1) InterviewAnswers
  │
  └──(1)───(N) Notifications
```

**Design rationale:** everything ultimately traces back to `Users` because the Performance Profile (dashboard/roadmap) needs to join across Submissions + ResumeAnalyses + InterviewSessions for one user cheaply — hence the consistent `userId` FK + index pattern across every module, even though they're logically separate "services."

## 13. API Design

| Endpoint | Purpose | Auth | DB / External |
|---|---|---|---|
| `POST /auth/register` | Create account (student/recruiter) | None | Writes `Users`, hashes password (bcrypt) |
| `POST /auth/login` | Authenticate, issue JWT pair | None | Reads `Users`, verifies hash |
| `POST /auth/refresh` | Rotate access token | Refresh token (cookie) | Redis (refresh token blacklist check) |
| `GET /jobs` | List/search/filter jobs | Optional (public can browse) | Reads `Jobs` (indexed, paginated) |
| `POST /jobs` | Create job | Recruiter JWT | Writes `Jobs` (status=pending) |
| `PUT /jobs/:id` | Edit job | Recruiter JWT (owns job) | Updates `Jobs` |
| `POST /jobs/:id/apply` | Apply to a job | Student JWT | Writes `Applications`, links active `Resumes` row |
| `GET /applications/me` | Candidate's application history | Student JWT | Reads `Applications` joined `Jobs` |
| `GET /jobs/:id/applicants` | Recruiter view of applicants | Recruiter JWT (owns job) | Reads `Applications` joined `Users`, `ResumeAnalyses` |
| `PATCH /applications/:id/status` | Change application status | Recruiter JWT | Updates `Applications`, enqueues notification |
| `POST /submissions` | Submit code for a problem | Student JWT | Writes `Submissions` (pending) → enqueues grading job → Judge0 (async) |
| `GET /submissions/:id` | Poll/check submission result | Student JWT (owns submission) | Reads `Submissions` |
| `GET /problems` | List coding problems | Optional | Reads `CodingProblems` |
| `POST /resume/upload` | Upload resume file | Student JWT | Pre-signed S3 URL flow → writes `Resumes` |
| `POST /resume/analyze` | Trigger ATS analysis (optionally vs a jobId) | Student JWT | Reads `Resumes`, calls text extraction + LLM, writes `ResumeAnalyses` |
| `POST /interviews` | Start a new interview session | Student JWT | Writes `InterviewSessions`, calls LLM for first question |
| `POST /interviews/:id/answer` | Submit an answer, get next question | Student JWT (owns session) | Writes `InterviewAnswers`, calls LLM for eval + next question |
| `GET /interviews/:id/result` | Get final interview feedback | Student JWT | Reads aggregated `InterviewAnswers` |
| `GET /dashboard/me` | Aggregated performance profile | Student JWT | Reads across Submissions/ResumeAnalyses/Interviews |
| `GET /admin/reports` | View abuse/moderation reports | Admin JWT | Reads `Reports` |
| `PATCH /admin/jobs/:id/moderate` | Approve/reject a job | Admin JWT | Updates `Jobs.status` |

All mutating endpoints: **input validated with Zod**, **rate-limited via Redis**, **wrapped in try/catch → structured error responses** (`{error: {code, message}}`), and **idempotency keys** honored on `POST /submissions` and `POST /jobs/:id/apply` to survive client retries safely.

## 14. Security Design

| Area | Approach |
|---|---|
| Authentication | JWT access (15 min) + refresh (7 days, httpOnly + Secure cookie), rotated on use |
| Passwords | bcrypt (cost ≥ 12), never logged, never returned in any API response |
| JWT/session security | Short-lived access tokens, refresh token rotation + blacklist in Redis on logout/compromise |
| RBAC | Middleware checks `role` claim on every protected route (student/recruiter/admin) |
| API security | Helmet headers, strict CORS allow-list, input validation on every endpoint |
| Rate limiting | Redis token-bucket: stricter on `/auth/*` (brute-force protection) and `/submissions` (abuse/cost control) |
| File uploads | Type/size validation client + server side, virus-scan hook (ClamAV, optional advanced), only pre-signed S3 uploads — file never passes through app server memory |
| Resume files | Stored in **private** S3 bucket, accessed only via short-lived pre-signed GET URLs |
| AI APIs | Gemini/Groq API keys stored in Render env vars (backend) or SSM Parameter Store (if called from the AWS side), never client-exposed; LLM responses schema-validated before use; prompt-injection defense — treat resume/JD text as **data**, never as instructions, using clear system-prompt boundaries; free-tier rate limits handled via the provider-fallback abstraction (§4.7), never surfaced as a raw error to the user |
| Database | Parameterized queries via ORM (Prisma) — no raw string concatenation → prevents SQL injection; least-privilege DB user (no superuser for app connections) |
| Secrets | Render/Vercel encrypted env vars for app-level secrets, AWS SSM Parameter Store (free) for anything the EC2/Judge0 side needs — never in repo, `.env` in `.gitignore` |
| CORS | Explicit origin allow-list, credentials only where needed |
| CSRF | Not a major risk for JWT-in-header APIs, but refresh-token cookie uses `SameSite=Strict` + CSRF token on any cookie-authenticated mutating route |
| XSS | React auto-escapes by default; sanitize any markdown-rendered content (problem statements, resume suggestions) with a strict allow-list sanitizer (e.g., DOMPurify) |
| SQL/NoSQL injection | ORM parameterization; if any raw queries are needed, always parameterized, never templated strings |
| **Judge0/code execution security** | See §3.10 in full — isolated sandbox (isolate), no network access from execution containers, strict CPU/memory/process limits, non-root execution, Judge0 never exposed directly to the public internet, dedicated network segment |
| Docker isolation | Judge0 containers run with dropped capabilities, read-only root filesystem where possible, no privileged mode |
| Network security | VPC private subnets for Judge0/DB, security groups scoped to specific source SGs (not `0.0.0.0/0`) |
| AWS IAM | Least-privilege roles per task (ECS task role scoped to only the S3 bucket/actions it needs), no long-lived root/admin keys in code |
| HTTPS | Enforced everywhere (Vercel/Render auto-TLS, ACM for any AWS-fronted endpoint), HSTS header |

## 15. Scalability

| Users | Expected Bottleneck | Mitigation |
|---|---|---|
| **~100** | None really — single small Postgres instance, single backend instance, direct Judge0 calls fine | Current architecture handles this trivially; focus on correctness, not scale |
| **~1,000** | Submission queue backlog during peak (e.g., a class deadline), LLM API latency/cost, DB connection count | Add more worker instances (horizontal scale, stateless), add Redis caching for job listings, add connection pooling (PgBouncer), batch/cache LLM calls where possible |
| **~10,000+** | DB read load on job search/listing, Judge0 throughput, LLM API rate limits/cost, single-region latency | Read replicas for Postgres, dedicated search index (OpenSearch) if full-text search on Postgres GIN index becomes slow, horizontally scale Judge0 workers across multiple ECS tasks/instances, introduce request queuing/backpressure with clear user-facing "queued" states, consider caching LLM responses for identical/similar resume-analysis requests, CDN for static frontend assets (Vercel handles this automatically) |

**General evolution path:** stateless API/worker instances behind a load balancer (scale horizontally by adding instances) → database read replicas for read-heavy endpoints (job search, dashboards) → dedicated search service only if/when Postgres full-text search demonstrably can't keep up → move Judge0 to a dedicated auto-scaling ECS service sized by queue depth (CloudWatch alarm on queue length triggers scale-out).

## 16. Complete User Flows

**1. Registration/Login**
User → Frontend (signup form) → `POST /auth/register` → Backend validates + hashes password → writes `Users` row → returns JWT pair → Frontend stores access token in memory, refresh in httpOnly cookie → redirects to dashboard.

**2. Solving a Coding Problem**
User → Frontend (`/problems/:id`, Monaco editor) → writes code → clicks "Run Sample" → `POST /submissions/run` (sample-only, synchronous, no DB write) → Judge0 → result shown inline.

**3. Code Submission through Judge0**
User → clicks "Submit" → `POST /submissions` → Backend writes `Submissions(status=pending)` → enqueues job (BullMQ) → returns `submissionId` (202) → Frontend polls `GET /submissions/:id` → Worker consumes queue → calls Judge0 per test case → aggregates verdict → updates DB → Frontend shows final verdict.

**4. Uploading a CV**
User → Frontend "Upload Resume" → `POST /resume/upload-url` (backend generates pre-signed S3 URL) → Frontend uploads file directly to S3 → Frontend confirms → `POST /resume/confirm` → Backend writes `Resumes` row.

**5. CV Analysis**
User → clicks "Analyze" → `POST /resume/analyze` → Backend fetches file from S3 → extracts text → calls LLM (structured extraction) → validates JSON schema → writes `ResumeAnalyses` (parsed data) → returns to Frontend.

**6. ATS Scoring**
Continuation of (5) → Backend runs deterministic scoring engine (keyword/skill/format rules, §4.3) against parsed data (+ optional JD) → writes `atsScore` + breakdown to `ResumeAnalyses` → Frontend renders score + breakdown chart.

**7. CV Optimization**
User views suggestions → `POST /resume/analyze` (LLM suggestion pass) → Backend returns suggestion list → User selects suggestions to apply → `PATCH /resume/:id` updates resume content/metadata → optional re-render to a new PDF version.

**8. Searching for a Job**
User → Frontend `/jobs?query=&filters=` → `GET /jobs` (indexed query, paginated) → Backend reads `Jobs` where `status=published` → returns paginated results → Frontend renders list.

**9. Applying for a Job**
User → clicks "Apply" → selects active resume → `POST /jobs/:id/apply` → Backend checks no duplicate application (unique constraint) → writes `Applications` → enqueues notification job → returns confirmation.

**10. Recruiter Creating a Job**
Recruiter → Frontend job form → `POST /jobs` → Backend validates, writes `Jobs(status=pending_moderation)` → notifies admin queue → returns job draft to recruiter (pending review).

**11. Recruiter Reviewing Applications**
Recruiter → `GET /jobs/:id/applicants` → Backend joins `Applications`+`Users`+`ResumeAnalyses`, sorts by matchScore → Frontend renders ranked table → Recruiter → `PATCH /applications/:id/status` → Backend updates + enqueues candidate notification.

**12. Starting an AI Interview**
User → selects type/difficulty → `POST /interviews` → Backend writes `InterviewSessions` → calls LLM for Q1 (seeded by question bank/template) → returns question → Frontend displays.

**13. Completing an AI Interview**
User answers each question → `POST /interviews/:id/answer` per turn → Backend evaluates + generates next question → loop until N questions done → Backend marks session `completed`, computes `overallScore`.

**14. Receiving Interview Feedback**
User → `GET /interviews/:id/result` → Backend aggregates per-question scores/weaknesses → returns summary + recommendations → Frontend renders feedback dashboard + updates Placement Roadmap.

### 19.4 AWS Architecture (One-Line Summary)

Minimal, free-tier-only footprint: VPC with a single free-tier EC2 instance running Judge0 (locked down by Security Group + shared secret, no NAT Gateway needed), S3 for files, IAM least-privilege roles, SSM Parameter Store for credentials, CloudWatch for observability — database and cache deliberately kept off AWS (Neon/Supabase + Upstash instead) since neither has a free-forever AWS equivalent.

### 19.5 Database Overview

12 core entities (§12) centered on `Users`, with clean FK relationships enabling a unified performance profile across coding, resume, and interview data.

### 19.6 API/Service Overview

REST API organized by module (`/auth`, `/jobs`, `/submissions`, `/resume`, `/interviews`, `/admin`), async-heavy design (submissions and AI calls always queued, never blocking).

### 19.7 Security Architecture

JWT auth + RBAC, rate limiting, input validation, sandboxed code execution (Judge0/isolate, no network, resource limits, private network placement), least-privilege IAM, secrets management, HTTPS everywhere.

### 19.8 Deployment Architecture

Vercel (frontend) + Render (backend/workers) + AWS (Judge0, S3, security infra) — three providers chosen deliberately per their strengths rather than "AWS for everything," with the security-critical execution engine isolated in a real VPC.

### 19.9 Development Roadmap (One-Line Summary)

15 phases: foundation → auth → DB → job portal → coding platform → Judge0 → resume/ATS → AI interview → Docker → AWS → Vercel/Render → CI/CD → security → testing → production polish.

### 19.10 System-Design Concepts Demonstrated

Modular monolith architecture, REST API design, JWT auth/RBAC, caching, DB indexing, pagination, rate limiting, async processing via queues, background workers, horizontal scaling, load balancing, fault tolerance/retries, idempotency, file storage via pre-signed URLs, sandboxed untrusted-code execution, VPC networking, IAM least-privilege, observability, and CI/CD — a coherent, defensible, portfolio-grade demonstration of full-stack + cloud + DevOps skill without artificial over-engineering.
